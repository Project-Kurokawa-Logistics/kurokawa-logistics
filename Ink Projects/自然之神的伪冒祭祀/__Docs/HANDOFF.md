# Work 模式交接：DeepSeek 实施，ChatGPT 审核

## 1. 交接目的

这份文件用于在后续 Work 模式会话中恢复项目背景，并规范实现与审核的分工。

用户计划由 DeepSeek 撰写实际代码，由 ChatGPT 负责独立审核。目标不是立即进行大规模重写，而是以可审查、可测试、可回退的小步骤逐步重构。

**本文件只定义交接与工作方式，不代表已经开始重构。** 当前交接提交不修改任何 Ink 剧情文件。

## 2. 开始前必须读取的资料

开始任何代码工作前，先读取最新 `main`，然后阅读：

1. [README.md](README.md)：文档索引。
2. [REFACTORING_SPEC.md](REFACTORING_SPEC.md)：完整重构规范。
3. [STORY_FLOW.md](STORY_FLOW.md)：现有剧情流程概览。
4. [INK_CONVENTIONS.md](INK_CONVENTIONS.md)：现有写法与建议规范。
5. [VARIABLES.md](VARIABLES.md)：变量索引。
6. [OPEN_ISSUES.md](OPEN_ISSUES.md)：尚未确认的问题。
7. 主入口 `自然之神的伪冒祭祀.ink` 及本次任务涉及的实际源码。

不要只依赖本文件或聊天摘要。仓库中的源码和最新提交才是执行时的事实基线。

## 3. 项目已确认的设计事实

### 3.1 项目定位
- 本作是黑川物流主线故事之后的独立 **1.5 周目**大型纯文本 RPG。
- Ink 用于灵活分支和 RPG 式状态玩法，不局限于传统线性互动小说。
- 本项目不负责设计黑川物流主线故事的二周目，也不应把跨项目状态/存档机制纳入本次架构。

### 3.2 场景与开局
- 森林、沙漠、深渊、城市等是大场景分区。
- 不同开局可能从不同地方开始，但探索过程中仍可能前往其他大场景。
- 不同开局暂时视为不同的世界发展分支，可能影响后续事件和人物生死。
- 各分支最终可能抵达同一目的地，但不能据此推断之前状态相同。
- **事件同步、人物生死、分支汇合规则尚未决定。** 实施者只能盘点现状并提出备选方案，不能自行设定。

### 3.3 回溯与职业
- AZ 已有回溯叙事表现；回溯后会有类似“似乎刚才走神了，想的有点多”的文本。重构不得删除或改变其含义。
- 叙事上的回溯不等于 Ink 已自动实现完整的运行时状态恢复；若涉及状态快照，必须先确认实际宿主环境。
- 角色职业标记**尚未实现**。仅可预留扩展空间，未经作者确认不得实现一套臆测的职业系统。

### 3.4 代码与目录
- 按大场景组织剧情，不按开局建立互不相干的全套副本。
- 剧情目录和文件不使用数字前缀排序；`__Docs` 可以保留置顶前缀。
- Ink 的 INCLUDE 不会创建文件级命名空间；knot 和全局变量仍需全局避免冲突。
- 本次交接只涉及文档；任何代码改动都必须另行规划、测试和审核。

## 4. 分工与决策权

### DeepSeek：实现者
负责：
- 阅读相关源码并给出简明的实施计划。
- 按批准的范围修改代码。
- 维护调用兼容性、更新必要文档。
- 运行可用的编译、静态检查与路线测试。
- 提供完整 diff、测试命令/结果和未解决问题。

不负责：
- 擅自决定开放设计问题。
- 为了整洁改写人物生死、事件同步、结局或选择含义。
- 将尚未实现的功能写成已实现。
- 声称执行过实际未执行的测试。

### ChatGPT：独立审核者
负责：
- 检查实施计划是否符合重构规范。
- 审核 diff 中的 Ink 语法、引用、状态生命周期和架构边界。
- 检查剧情跳转、人物状态、物品数量与结局逻辑是否有未经授权的变化。
- 对照测试证据判断验收是否充分。
- 将问题按严重程度列出，给出可执行的修正建议。
- 明确区分已证实缺陷、潜在风险和需要作者决定的问题。

ChatGPT 不应仅因为代码看起来整洁就批准改动；也不得在未实际执行测试时声称测试通过。

### 用户/作者：最终设计决策者
以下事项必须由作者决定：
- 不同开局对事件与人物生死的影响。
- 不同世界发展分支如何汇合。
- 职业标记的含义与玩法。
- 回溯后的状态保留规则。
- 任何会改变剧情结果或玩家体验的行为修改。

遇到这些问题时，DeepSeek 应暂停相关行为改动并列出选项；ChatGPT 应标记为“需要作者决定”，不能替作者定案。

## 5. 每次代码任务的标准流程

### 第 0 步：确认工作区
- 读取最新 `main` 和当前分支状态。
- 记录起始 commit SHA。
- 检查工作区是否存在其他未提交改动。
- 不要覆盖或丢弃其他人的工作。

### 第 1 步：盘点并提案
DeepSeek 先阅读任务涉及的文件，提交一份短计划，说明：
- 本次要解决的问题。
- 预计修改的文件。
- 可能影响的变量、knot、INCLUDE 和路线。
- 风险与测试计划。
- 是否涉及开放设计问题。

在计划未审核前，不进行大范围代码修改。简单、无行为变化的机械操作可在明确范围后执行。

### 第 2 步：建立基线
尽可能运行项目实际使用的 Ink 编译器/运行器，记录原有错误和可运行路线。若工具链不可用，明确说明，不得将“无法测试”写成“通过”。

### 第 3 步：小批次实现
- 一批只处理一个明确目标。
- 先做结构迁移，再做行为修改；避免同时进行。
- 保留现有 knot/变量名，除非改名属于本次批准范围。
- 对所有路径变化检查 INCLUDE。
- 对变量变化检查初始化、写入、读取和重置。
- 不顺手清理无关代码。

### 第 4 步：提交证据
DeepSeek 提交可审查 diff，并报告修改、测试和遗留问题。后续实际代码优先在工作分支上提交，再通过 PR 审核；不要未经审核直接写入 `main`。

### 第 5 步：ChatGPT 审核
按第 6 节的清单审核。若有阻塞问题，列出具体文件/节点/条件和修复建议，要求 DeepSeek 修正后重新提交 diff。

### 第 6 步：验收与合并
只有在阻塞问题处理完、测试结果如实记录、开放问题已标明后，才建议合并。合并后核实 `main` commit 与最终文件。

## 6. ChatGPT 审核清单

### A. 范围与架构
- [ ] 是否符合 `REFACTORING_SPEC.md`？
- [ ] 是否按大场景组织，而非按开局复制整个世界？
- [ ] 是否避免剧情目录数字前缀？
- [ ] 是否把通用系统和具体剧情职责分清？
- [ ] 是否引入了不必要的抽象或空模块？

### B. Ink 结构
- [ ] 所有 INCLUDE 路径都有效。
- [ ] 所有被改动的 knot/变量名称均已检索引用。
- [ ] 无新增重名 knot 或重复变量声明。
- [ ] 跨文件跳转目标存在。
- [ ] 对 Ink 语法与宿主标签的假设有实际依据。

### C. 行为保持
- [ ] 选项条件与选项文字没有未经授权的改变。
- [ ] 跳转目标与路线可达性没有意外变化。
- [ ] 人物生死、事件先后、角色关系没有被擅自改变。
- [ ] 物品增减、变量写入和重置逻辑有依据。
- [ ] AZ 的既有回溯文本与行为保留。
- [ ] 未把职业标记写成已实现功能。

### D. 测试与证据
- [ ] 编译命令、工具链版本和结果已记录（若可用）。
- [ ] 测试覆盖与本次改动范围匹配。
- [ ] 未覆盖的路线和工具限制已明确说明。
- [ ] 没有把静态阅读当成运行时验证。
- [ ] 没有声称执行过实际未执行的命令。

### E. 文档与交付
- [ ] 相关文档已更新。
- [ ] 变更集中且 diff 易于审核。
- [ ] 已知问题没有被悄悄删除。
- [ ] 提交信息清楚，分支与 PR 状态明确。

## 7. 问题严重程度

审核反馈按以下等级分类：

- **P0 — 阻塞/数据破坏：** 可能破坏存档/状态、导致无法运行或大范围路线损坏。禁止合并。
- **P1 — 剧情或逻辑回归：** 错误跳转、状态重置错误、物品数量异常、人物/结局行为被改变。修复前禁止合并。
- **P2 — 维护性/覆盖不足：** 结构不清、遗漏文档、测试覆盖不足或存在明显潜在风险。通常应修复或明确接受风险后再合并。
- **P3 — 风格建议：** 不影响行为的命名、格式或可读性建议。可记录，不必阻塞所有任务。

审核意见必须指出具体依据，避免只说“代码不够整洁”。

## 9. 当前已知风险与待决定事项

这些条目来自当前文档和此前静态阅读，应在实施时重新核实，不应视为最新源码审计的最终结论：

- 不同开局造成的事件同步与人物生死差异尚未设计完成。
- 职业标记尚未实现。
- 回溯后的实际状态恢复能力取决于宿主运行环境；现有叙事表现必须保留。
- 物品列表与独立数量变量的关系需要确认，移除操作需要边界校验。
- `TEMP__` 前缀不代表 Ink 局部变量，需要检查生命周期。
- 某些路线、结局跳转、禁用选项和 TODO 需要基于最新源码逐项复核。
- 当前项目的实际编译工具链与宿主对自定义标签的解释方式，必须在实施前确认。

## 10. 安全边界

- 不擅自改变用户没有授权改变的故事行为。
- 不删除未知用途的变量、节点或调试入口，除非先查明并获得授权。
- 不强制合并不同开局的状态。
- 不自行设定人物生死、职业系统或回溯规则。
- 不直接覆盖他人提交；遇到 main 更新时先同步最新状态。
- 不把未运行的测试标记为通过。
- 发现规范与源码冲突时，先报告冲突；源码可能是现状，规范可能是目标，不能自动假定其中一方应该被改掉。

## 11. 首个建议任务

进入 Work 模式后，不要立刻全面重构。建议先执行一个只读盘点任务：

1. 读取最新 main 与本目录全部文档。
2. 列出实际目录、INCLUDE、knot、全局变量与系统函数。
3. 查明可用的 Ink 编译器/运行器与现有测试方式。
4. 建立“当前现状 / 目标结构 / 迁移映射 / 风险 / 待作者决定”报告。
5. 不修改任何源码，等待 ChatGPT 审核盘点结果。

盘点审核通过后，再从一个范围小、行为容易验证的模块开始。
