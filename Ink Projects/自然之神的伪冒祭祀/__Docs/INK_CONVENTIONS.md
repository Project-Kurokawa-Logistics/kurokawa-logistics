# Ink 编写约定

本文把“当前源码中能观察到的写法”与“建议统一采用的维护规范”分开记录。建议不应被误认为所有旧脚本已经遵守。

## 1. 当前项目中可观察到的写法

| 用途 | 当前可见写法 | 说明 |
|---|---|---|
| 汇总脚本 | INCLUDE Maps/Forest/FarMoriTown.ink | 主文件通过 INCLUDE 汇总多个文件。新增脚本时也要检查主文件是否需要 INCLUDE。 |
| 文件入口 knot | === Forest__FarMoriTown | 多个地图文件以带路线前缀的 knot 开头。 |
| 同文件内节点 | = GoTown | 文件内使用多个具名节点。 |
| 跳转 | -> Find_Base | 目标名称必须存在且拼写一致；跨文件节点在当前源码中也有 -> Forest__Dungeon.Stop_Commercial 这种限定写法。 |
| 选项 | + [寻找住的地方]、* [继续] | 项目中同时使用 + 与 *。新增选项应按 Ink 语义与实际需要选择，并通过运行测试确认行为。 |
| 条件选项 | + {TEMP__Flag == 0}[选项] | 条件不满足时该选项不会按此条件显示。 |
| 条件文本 | - Careers__AZ != "神官": | 用条件分支控制后续文本/跳转。 |
| 变量声明与赋值 | VAR Count__Chapter = 0、~ Count__Chapter ++ | 变量通过声明初始化，后续用 ~ 语句修改。 |
| 结局记录与返回菜单 | <- Finales.PoChan 后接 -> Menu__Finale | 这是当前项目中出现的成对写法。新增结局分支前应复制已确认可运行的模式，不要在未测试时自行推断 <- 的具体运行语义。 |
| 注释/标记 | TODO、⛔️、# unclickable、# CLEAR | 这些标记出现在现有源码中。其对运行时/UI 的影响取决于项目使用的 Ink 工具链或宿主程序，不能把它们都当成 Ink 原生控制流。 |

## 2. 建议采用的命名规则

以下为建议，不是对现有命名的强制重命名要求：

- 路线入口采用可辨识的前缀，例如 Forest__、Abyss__、Ruoment_City__。
- 节点名尽量表达动作或场景，例如 Find_Base、Stop_Rite、Select__Career。
- 新变量应能从名称看出用途，避免同一变量兼任章节进度、剧情条件与 UI 状态。
- TEMP__ 在当前项目里是变量名前缀。由于源码中使用 VAR TEMP__... 声明，不能只凭前缀就认为它具有 Ink 的局部临时变量生命周期；需要明确它何时初始化、重置，以及是否会跨节点保留。
- 结局标记应与 Misc/Finales.ink 中的目录条件保持一致，并记录由哪个剧情节点设置。

## 3. 新增分支时的建议流程

1. **先确定节点关系**：入口、可选分支、成功/失败/返回路径，以及哪些选择会结束当前章节。
2. **再写选项和条件**：每个可见选项都应有明确的目标节点，或明确标识为暂时不可用。
3. **管理变量生命周期**：声明初值；记录何时递增/赋值；说明何时重置；确认回到节点时是否会再次显示已经选择过的选项。
4. **检查所有跳转目标**：INCLUDE 会把多个文件汇总进同一故事，新增 knot 时应避免与其他文件中的名称冲突。
5. **保持结局调用模式一致**：涉及 Finales.* 的分支，先参考当前已知模式，并在目标运行环境中验证。
6. **同步维护文档**：更新故事流程、变量索引与待办清单。
7. **实际验证**：若有 Ink 编译器/游戏运行器，先编译，再走通新增分支和相邻返回路径。

## 4. 未开放选项的处理

当前源码会用 ⛔️、# unclickable 和 TODO 标注未完成内容。建议未来统一采用以下记录方式：

- 选项文案保留时，写明 TODO 负责人/目的（如果项目有负责人机制）。
- 文档里登记对应文件、节点、预期行为与依赖条件。
- 若某个选项只是为了临时让流程继续，不要把它误记为已实现的功能。
- 完成后同时移除过时标记并检查是否仍有死节点或无入口节点。

## 5. 文本与剧情连续性

- 一个选项如果会改变人物身份、阵营、种族或关系，应明确写入状态变量或在文档中说明其仅为叙事分歧。
- 同一角色的名字、别名、阵营与转化状态应在跨章节时保持一致；如果身份变化是剧情重点，应在文本中明确交代。
- 不要因为节点名称带有 Ending 就假定它是最终结局；追踪实际跳转后再分类。
- 未经作者确认的推断请记为“待验证”，不要直接改写成既定世界观。
