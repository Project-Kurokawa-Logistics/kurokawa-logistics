# 完全重构规范：自然之神的伪冒祭祀

- **状态：** 重构基准草案；实施前由作者确认具体改动范围
- **适用范围：** 本目录下的 Ink 项目、剧情组织、状态管理、系统模块和维护流程
- **基线：** 以开始每一阶段时最新的 `main` 为准；不要假定历史提交仍是当前版本
- **核心要求：** 先保证剧情行为可追踪、可验证，再改善结构；重构不得暗中改写设计

## 1. 项目定位与边界

### 1.1 本项目是什么

《自然之神的伪冒祭祀》是黑川物流主线故事之后的独立 **1.5 周目**大型纯文本 RPG 项目。Ink 不仅用于线性互动小说，也用于承载灵活分支、状态、物品、角色与探索等 RPG 玩法。

本项目可以包含多种开局、森林/沙漠/深渊/城市等大场景、跨区域探索、物品与命名系统、角色状态、章节、成就、结局、死亡和读档表现，以及未来经作者确认的其他互动功能。

### 1.2 本项目不负责什么

- 不将黑川物流主线故事的“二周目”作为本项目的架构目标。
- 不将本项目改造成主线故事的附属章节或共享运行时。
- 不因未来可能发生的主世界剧情而提前设计跨项目存档、共享状态或多项目引擎。
- 不在重构中擅自改变人物生死、事件先后、结局含义或玩家选择的结果。
- 不把尚未实现的职业标记、复杂回溯状态恢复等写成现有功能。

### 1.3 设计事实与开放问题必须分开

本文中：
- **已确认设计**：作者已经明确的项目定位和要求。
- **当前源码事实**：能在现有文件中直接确认的行为。
- **建议**：供重构参考，尚不等于已获准改变。
- **开放问题**：作者尚未决定；实施者不得自行填补答案。

## 2. 总体架构原则

1. **剧情优先。** Ink 仍然负责叙事、选项、条件与分支。不要为了抽象而把所有剧情都改成系统调用。
2. **按大场景组织剧情。** 森林、沙漠、深渊、城市等是长期的内容分区。不同开局不等于各自拥有完全隔离的剧情副本。
3. **系统职责清楚。** 通用库存操作、名称获取、成就记录、结局记录、初始化和调试等可复用逻辑应逐步集中。
4. **状态来源唯一。** 表达同一事实的多个变量不能在没有同步规则的情况下各自充当权威来源。
5. **保留有意义的分支差异。** 不能为减少重复而合并本来会导致不同事件或人物生死的路线。
6. **避免大爆炸式重写。** 先盘点、再迁移；每批只改一类问题，并留下可回退的 Git 提交。
7. **不提前建造未来系统。** 先记录设计边界；只有需求明确时才实现模块。
8. **不以文件数量衡量整洁度。** 按职责和剧情边界拆分，而不是每个 knot 一个文件。

## 3. 目标目录组织

以下是目标方向，不要求一次性创建所有文件，也不代表必须采用每个示例文件名：

```text
自然之神的伪冒祭祀/
├── 自然之神的伪冒祭祀.ink     # 唯一主入口与 INCLUDE 清单
├── __Docs/                    # 设计、交接、流程、规范、待办
├── Core/                      # 核心状态、初始化、调试入口
├── Characters/                # 角色基础信息与角色状态
├── Systems/
│   ├── Inventory/             # 物品定义与库存操作
│   ├── Identity/              # 命名与身份显示
│   ├── Progression/           # 章节/成就/结局记录
│   └── Rewind/                # 仅在需要集中管理时建立
├── Functions/                 # 通用、可复用的辅助函数

└── Regions/

    ├── Desert/

    └── Ruoment_City/
```

### 3.1 数字前缀规则

- 剧情目录与剧情文件不使用 `01_`、`02_` 等数字前缀来表示顺序。
- `__Docs` 可以保留前缀，以便在目录中置顶。
- 剧情顺序由入口、显式跳转、条件和必要的 INCLUDE 顺序表达，不依赖文件名排序。
- 不要仅为符合目标树而批量移动文件。先做映射，逐批迁移。

### 3.2 从现有 Maps 迁移到大场景目录

当前主入口使用 `Maps/Abyss/`、`Maps/Forest/`、`Maps/Desert/` 和 `Maps/Ruoment_City/` 等路径。未来可以逐步迁移到 `Regions/`，但目录名称本身不是重构成功标准。

迁移必须同步更新 INCLUDE 与文档链接，并确认没有路径引用遗漏。若移动成本高或宿主工具依赖现有路径，可先保留 `Maps/`，只在内部逐步整理。

### 3.3 大场景内部拆分

只有当文件包含多个相对独立的场景/章节、职责混杂或维护困难时才拆分。优先按场景与章节边界，而非按 knot 数量拆分。拆分前记录旧 knot 到新文件的映射。

## 4. 主入口与 Ink 命名空间

### 4.1 主入口职责

主文件应主要负责：
- 项目元数据；
- 有意排序的 INCLUDE 清单；
- 进入标题/初始流程的唯一入口。

不应继续积累大段具体场景文本或重复的系统实现。

### 4.2 INCLUDE 与全局命名

Ink 的 INCLUDE 将脚本汇入同一个 Story，并不会自动给每个文件建立独立的 knot/变量命名空间。

- 全局 knot 名称与变量声明必须避免冲突。
- 修改文件路径后，检查所有 INCLUDE。
- 移动或重命名 knot 后，检查所有跳转与引用。
- INCLUDE 的排序应根据实际依赖和现有工具链验证，不能只照抄目录顺序。
- 不能只凭静态阅读声称所有 knot 均可达或可编译。

### 4.3 Knot 命名

尽量保留现有名称，例如 `Forest__FarMoriTown`、`Abyss__...` 等路线/场景前缀。新节点使用能表达场景或用途的名称，避免含糊缩写；具体风格以现有项目约定为基础。

不要在一次纯结构重构中同时大规模重命名 knot。若确需重命名，应独立提交，并列出所有受影响的跳转。

## 5. 状态、变量与生命周期

### 5.1 建议的状态分类

分类是文档与审查概念，不要求立即创建同名对象或文件：

- **世界状态：** 当前地点、物品库存、任务进度、角色状态等。
- **角色状态：** 名称、种族、身份、关系及未来职业标记。
- **剧情状态：** 分支旗标、事件是否发生、章节推进。
- **回溯叙事状态：** 与 AZ 记得什么、如何表现回溯有关的标记。
- **记录/进度状态：** 成就与已经历结局等。
- **线路记录状态（目标设计）：** 各开局线路的完成标记与重试次数标签，可在独立线路进程之间读取，不等同于线路内世界状态。
- **界面/调试状态：** 菜单行为、测试入口与临时 UI 旗标。

这些分类不能自动决定一个状态在读档、重开或章节跳转时应保留还是清除；每个变量的生命周期仍需明确。线路完成标记与重试次数标签可以跨线路读取，也不表示其他状态天然具有相同的保留范围。

### 5.2 重要变量登记

在 `VARIABLES.md` 中逐步登记重要变量的：
- 初值与用途；
- 写入、读取位置；
- 重置位置；
- 是否跨场景/章节保留；
- 受哪些开局或剧情条件影响；
- 对应的测试方法。

`TEMP__` 只是项目的命名前缀。通过 `VAR TEMP__...` 声明的变量仍然是全局变量，不能因名字而假定它会自动清除。

### 5.3 初始化与重置

必须区分并审查：
- 新游戏初始化；
- 同一线路内的重新开始或重试；
- 完成一条开局线路后的再次开局；
- 从调试菜单跳转到章节；
- 重返已访问场景；
- 结局后返回菜单；
- 未来若需实现的状态回溯。

这些入口不一定应该执行相同的重置。重构者必须先记录当前行为，未经授权不得自行改变。再次开局时不提供二周目加成是已确认设计，但各变量如何落地初始化和保留仍需逐项映射。

## 6. 开局与世界发展分支

### 6.1 已确认的多线路进程规则

- 每条开局线路都是独立的游戏进程，直到该线路通关；线路完成后设置对应的完成标记。
- 再次开局可以选择不同线路，没有二周目加成。
- 某些不显眼的位置可以读取已完成线路的标记和重试次数标签。
- 全部开局线路完成后，在故事结局之后进入真结局，AZ 真正觉醒。
- 线路内没有硬性多周目要素；真结局要求每条开局线路都完成过。

以上是作者已确认的目标设计，不代表当前源码已经实现线路完成标记、重试次数标签、全线路判定或真结局。

### 6.2 状态与回溯边界

- 线路是独立进程，不能为了消除重复而强行同步线路内的人物生死、事件结果或其他世界状态。
- 线路完成标记和重试次数标签属于跨线路记录，不得转化为线路内能力、资源或其他二周目加成。
- 现有 `Count__Start`、结局／死法访问计数等不能直接等同于上述新记录；变量名、数据形式、写入点和读取点需要另行设计。
- 其他物品、角色、成就、结局和死法记录的生命周期仍需逐项映射，不能根据“独立进程”擅自全部清零或全部保留。
- 再次开局与 AZ 的叙事回溯是不同概念；本规则不授权改变既有回溯文本或把回溯实现成状态快照恢复。

### 6.3 尚未决定的细节

- 每条线路的标识、完成条件和完成标记写入点。
- 重试次数的统计范围、递增时机及具体读取位置。
- 全部线路的集合、真结局的具体入口和衔接剧情。
- 不同发展中的公共剧情、条件分支或专属剧情，以及共同目的地前后的具体分歧。
- 除完成标记和重试次数外，其他记录的跨线路保留规则。

实施者只能根据已确认边界盘点现状并提出映射方案，不得自行补齐上述细节。

### 6.4 公共内容的抽取

只有在叙事前提与状态条件相容时，才将不同路线的共同文本抽成公共节点。若人物状态或前置事件不同，应保留条件分支或独立场景，不要为了消除重复而改变剧情含义。

## 7. 物品系统

### 7.1 职责

物品系统应逐步统一物品标识、数量、添加/移除、查询、拥有判断与参数校验。剧情负责决定何时获得或使用物品；背包界面负责展示，不应另外维护一套库存真相。

### 7.2 唯一权威库存

当前项目有物品列表和独立数量变量。重构前必须确认列表是“当前持有物品”还是“曾经发现的物品”。

- 若列表代表当前库存，应明确数量与列表的同步规则，或考虑由数量推导持有状态。
- 若列表代表发现记录，应与当前库存分离并清楚命名。
- 不得让多个变量无规则地表示同一事实。

### 7.3 边界条件

检查未知物品 ID、负数/非法数量、数量不足时移除、移除后数量为零、重复添加/移除和列表同步。不能让未定义的输入造成负库存或状态不一致。

### 7.4 扩展节制

装备、合成、任务物品、分类和特殊使用效果均可作为未来扩展，但先满足现有玩法；不要提前构建过度通用的物品引擎。

## 8. 命名、身份与职业标记

- 内部角色身份应尽量稳定；显示名称可以改变。
- 命名系统负责统一名称获取/显示，避免剧情分支依赖易变的显示字符串。
- 现有 `Careers__AZ` 等变量应先盘点用途与引用，不能直接批量替换。
- **职业标记目前尚未实现。** 本次架构只预留扩展空间，不得把它写成已经可用的系统。
- 将来设计职业系统时，须先由作者决定职业是否可变、是否允许多个职业、是否影响选项/能力，以及内部标识和显示名称如何对应。

## 9. 结局、死亡与回溯

### 9.1 现有叙事必须保留

AZ 的回溯叙事已经存在。回溯后，AZ 会出现类似“似乎刚才走神了，想的有点多”的表现。这是已有叙事特征，结构重构不得删除或改写其含义。

### 9.2 结局分类

文档与代码审查应区分：
- 场景结束；
- 章节推进/检查点；
- Game Over；
- 可回溯的坏结局；
- 结局目录记录；
- 各线路的故事结局；
- 全部线路完成后、在故事结局之后进入的真结局（已确认目标设计：AZ 真正觉醒，当前源码尚未实现）。

节点名称包含 `Ending` 并不足以判定它是最终结局，必须追踪实际跳转。真结局的全线路完成判定与普通线路结局、结局目录访问记录也必须分开。

### 9.3 叙事回溯与状态恢复

叙事上表现为回溯，不代表 Ink 会自动恢复任意时间点的全部 Story 状态。任何涉及真正恢复状态的改动，都必须先确认实际宿主环境的能力与保存机制。

不得未经作者批准决定回溯后哪些物品、人物状态、事件记录或结局记录保留。先记录现有行为，再提出方案。

## 10. 菜单、页面与调试

- 通用菜单与导航放在菜单模块；具体剧情选择仍可留在场景文件。
- 结局触发、结局记录、目录显示和结局文本是不同职责，应可分别追踪。
- 调试入口、章节跳转、测试用状态修改应逐步集中管理。
- 未经授权，不得删除现有调试能力或改变玩家可见的菜单行为。
- 对 `# unclickable`、`# CLEAR` 等标签，先确认宿主/UI 的实际解释方式，不要把它们一概视为 Ink 原生控制流。

## 11. 迁移流程

### 阶段 A：只读盘点（已完成）
已盘点文件、INCLUDE、knot、变量、物品函数、开局、结局与主要 TODO；后续若源码变化，应按任务范围复核而不是重复全量盘点。

### 阶段 B：文档与验证基线（已完成）
已整理当前设计和源码事实，并在 `__Tests/` 建立项目自己的 inkjs 编译与行为回归。命令、结果和未覆盖范围见 `TESTING.md`。

### 阶段 C：角色命名／状态兼容接口
先区分名称、社会身份、职业、种族、状态和阵营，保留旧变量并设计兼容读取与迁移映射。每次只接入一类引用，不实现未经批准的职业系统。

### 阶段 D：物品公共接口
先通过现状测试明确调用兼容性，再逐步统一查询、持有判断和增减接口。非法数量、未知物品和库存不足等行为修复另行审批。

### 阶段 E：统一初始化
在线路完成标记、重试标签和其他状态的跨线路生命周期明确后，再设计新游戏、重开、章节跳转和重返场景的初始化；不得提前全部清零或全部保留。

### 阶段 F：按完整场景逐章迁移
逐批迁移完整场景，保留 knot 名称、选项、跳转和分支行为，更新 INCLUDE 与文档，并逐章编译和运行路线对照。

### 阶段 G：结局、死法、调试与界面
在路线和状态基线稳定后，再整理结局、死法、调试入口和界面抽象。职业标记及多线路新记录在具体设计获批前继续保持未实现。

每阶段可单独验收、提交和回退。不要把所有阶段合成一个不可审查的大改动。

## 12. 测试与验收

### 12.1 静态检查
- INCLUDE 路径存在且顺序经过确认。
- knot 和变量没有新增的重复定义。
- 跳转目标存在，跨文件引用已检查。
- 变量有清楚的初始化与生命周期说明。
- 物品增减边界经过检查。
- 未完成路线明确标记，未把 TODO 当作已实现功能。

### 12.2 行为回归
按当前可运行路线检查标题/开局、各大场景入口、主要章节、跨场景移动、物品增减、命名引用、坏结局/死亡/回溯表现、结局目录、重开与调试入口。

重构前存在的缺陷应记录为基线问题；不得假装它们是重构新引入或已被修复。

### 12.3 行为保持原则
纯结构重构不得未经批准改变：
- 选项显示条件与文本；
- 跳转目标与路线可达性；
- 人物生死和事件先后；
- 变量写入、物品数量与章节状态；
- 结局触发；
- AZ 回溯后的既有叙事表现。

如确需改变行为，先把它列为独立变更并说明理由，等待作者确认。

### 12.4 完成标准
一批改动只有在 diff 可审查、引用检查完成、适用测试已执行、文档同步、未验证事项明确记录后，才可标记为完成。没有运行测试时必须如实写明。

## 13. Git 与交付约定

- 开始工作前先读取最新 `main`，不要依赖旧对话中的 SHA 或文件快照。
- 作者已授权后续改动直接在 `main` 上小步实施和提交；每批仍须先明确范围，保持 diff 可审查、测试可复现、提交可回退，不得借此绕过剧情与行为变更审批。
- 文档或代码每次提交应聚焦单一目的，提交说明应可读。
- 不使用 force push 覆盖他人提交；若分支 HEAD 已变化，重新读取并基于最新状态继续。
- 不得把未运行的测试写成通过。
- 不得把静态推断写成已确认的剧情设定。

## 14. 开放设计问题

多线路独立进程、无二周目加成、完成标记与重试标签可跨线路读取，以及全线路完成后进入真结局，已经是确认规则，不再作为未决方向。以下实现与剧情细节仍由作者决定：

1. 各线路的标识、完成条件和完成标记写入点。
2. 重试次数的统计范围、递增时机和具体读取位置。
3. 全部线路的集合、真结局入口及 AZ 觉醒的衔接剧情。
4. 各路线在共同目的地前后，哪些内容汇合、哪些继续分歧，以及人物生死和事件状态如何体现。
5. 除完成标记与重试标签外，其他状态的跨线路保留规则。
6. 职业标记的语义与具体玩法。
7. 回溯的技术实现与回溯后各类状态的保留规则。
8. 物品系统未来是否需要装备、合成或其他高级能力。
9. 最终文件拆分粒度与 `Maps/` 是否迁移为 `Regions/`。

在获得决定之前，重构者可以盘点现状并提供备选方案，但不能自行定案。

---

## 最终原则

重构的成功标准不是文件夹看起来更漂亮，而是项目在保留剧情意图的前提下，更容易阅读、扩展、测试和审核。

**先理解现状，再提出计划；先保证行为可验证，再移动代码；遇到设计空白时提问，不擅自替作者写设定。**
