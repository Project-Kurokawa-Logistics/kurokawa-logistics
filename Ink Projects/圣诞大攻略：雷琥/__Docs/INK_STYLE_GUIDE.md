# Ink 脚本维护规范

本文档是本作品的建议维护约定，不代表当前所有源码已经完全符合。若要调整现有写法，先确认 Ink 编译器版本和宿主运行环境支持对应语法。

## 1. 文件与 Knot 组织

- 继续沿用主文件的 INCLUDE 清单组织故事；新增文件时同步更新 [`圣诞大攻略：雷琥.ink`](../圣诞大攻略：雷琥.ink)。
- 一个文件尽量负责一个清晰的场景或系统：主线、场景、变量/回顾、结局、结束界面等。
- Knot / Stitch 名称应唯一、稳定、可搜索。中文显示文案可以调整，但被其他文件引用的 Knot ID 不要随意重命名。
- 修改 Knot 名称前，全仓搜索所有 divert、条件和回顾菜单引用；不要只改定义处。
- 结局统一使用 `Finale.F1` 至 `Finale.F11` 这样的稳定入口，结局后的通用内容通过 `TheEnd` 进入。

## 2. 变量管理

- 新增全局变量时，在 [`Z_VAR.ink`](../Z_VAR.ink) 集中声明，并注明用途与预期取值。
- 在 `CleanData` 中维护需要每周目重置的数值变量清单。
- 跨周目解锁不要仅靠普通好感度变量；若依赖 Knot 访问记录，要在故事文档中写清楚前置条件，并测试返回标题、继续游玩和 RESTART 的行为。
- 变量名要体现用途；好感度、人物倾向、结局是否真正达成，属于不同状态，不应共用一个变量表达。
- 如果要追踪“结局已达成”，建议使用独立的结局完成状态，而不是直接把 Knot 是否被访问当作完成状态，尤其当该 Knot 还承担分流功能时。

## 3. 选择与分支

- 使用 `+` 表示一次性选择；如需选择在后续循环中仍可重复出现，应根据设计确认是否使用 `*`。
- 使用 `-` 作为选择组的 gather/汇合点前，确认所有选项都应汇合到同一处；若分支要继续到不同场景，需显式写出 divert。
- 对条件分支使用明确的数值比较。例如要判断 A 是否大于 B、C，应分别写出 A 与 B、A 与 C 的比较；不要用逻辑 `or` 代替“取较大值”或“与两个数值分别比较”。
- 分支条件要覆盖并列值、全为 0、最高值并列、阈值边界等情况；明确设计平局时走哪个分支。
- 选择文案相同且结果相同的多个选项应有明确的叙事目的，否则应合并或补充不同后果。
- 使用命名选项标签（例如 `(Tune_On)`）时，保持标签稳定，并检查所有通过该标签判断的条件。

## 4. 结局登记清单

新增、删除或改名结局时，至少检查以下位置：

1. `Z_Finale.ink`：结局正文与入口。
2. `Z_VAR.ink` 的 `CountFinale`：统计逻辑。
3. `Z_VAR.ink` 的 `FinaleList`：只显示已访问/已解锁结局的回顾列表。
4. `Z_VAR.ink` 的 `All_Finale`：全部结局目录。
5. 主文件标题说明中的结局总数与分类。
6. `STORY_FLOW_AND_ENDINGS.md`、`LOGIC_AUDIT.md` 和测试清单。

不要只更新菜单标题而忘记统计、解锁条件和文档。

## 5. 跨文件修改

- 对共享变量、结局 ID、入口 Knot 的修改，应同时检查所有引用。
- 文本润色尽量不混入逻辑重构；逻辑重构也尽量不大范围改写剧情文本，以便审阅差异。
- 在一个改动中明确记录预期行为、修改文件和测试路径。
- 不要把“脚本能编译”当成“所有分支正确”：编译后仍需按测试清单验证选择可见性、变量变化、divert 目标与结局计数。
- 如果当前环境没有可用的 Ink 编译/运行工具，应在提交说明中明确写“未执行运行时验证”，不要宣称测试通过。
