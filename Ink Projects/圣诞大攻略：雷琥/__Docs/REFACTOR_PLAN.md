## 1. 重构目标

本次重构不是重写故事，而是把现有设计表达得更明确、可维护、可测试：

1. 保留原作叙事意图，包括故意重复的选项、没有额外数值后果的角色扮演选项、现有剧情文本和开发者菜单。
2. 把“角色选择记录”“正片结局达成记录”“开发者预览状态”拆分为不同概念。
3. 让结局回顾只列出玩家通过正片实际走到的结局，而不是仅仅访问过对应 Knot 的结局。
4. 避免开发者菜单直接预览结局后，污染正式结局统计或意外满足多周目解锁条件。
5. 保留现有多周目体验，并明确新周目重置哪些数据、不重置哪些数据。
6. 每项逻辑修改都配套回归测试；不以“能编译”替代“行为正确”。

## 3. 建议的状态模型

### 3.1 三类状态必须分开

**A. 当前周目的数值状态**

当前路线判断使用以下变量：

- `Rate_LeiHu`
- `Choose_YeHen`
- `Choose_CenYe`
- `Choose_LeiHu`
- `Dormitory_LeiHu_Direct`：2026-10-29 新增的当前周目布尔状态，表示本局开场选择过“雷琥的事”，即 RAW 所说的“直接导向雷琥线结局”。它不是正式结局记录。

这些变量用于当前路线判断和调试显示。开始新周目时由 `CleanData` 重置（`Dormitory_LeiHu_Direct` 一并重置为 `false`）。

**B. 正片结局达成状态**

已在 `Z_VAR.ink` 中新增一组布尔变量：

- `Ending_F1_Achieved` 到 `Ending_F11_Achieved`，初值均为 `false`。

它们表示“是否至少通过正片完整达成过这个结局”，而不是“是否进入过这个 Knot”。每个结局只记一次，重复达成不增加结局总数。

这些标记**不应写进 `CleanData` 的重置列表**，这样普通的“再攻略一次”不会抹去已达成结局。按当前作品提示，玩家主动使用 RESTART 会重置 Ink 整个故事状态；是否需要跨 RESTART 持久化，属于另一项存档设计，不在本次最小重构范围内。

**C. 开发者预览状态**

已新增短生命周期布尔状态 `IsPreviewMode`，从结局回顾或开发者菜单直接查看结局时设为 `true`。

- 从 `All_Finale` 进入任意结局前开启预览状态。
- 在结局完成/统一结束流程中清除预览状态。
- `CleanData` 也将该状态设为 `false`，避免异常退出后影响新周目。
- 预览状态不能被当成正式解锁或达成标记。

## 4. 结局记录与菜单的具体改法

### 4.1 只在结局真正结束时记账

F1–F7、F9–F11 应在各自结局正文末尾、跳转到 `TheEnd` 之前记录达成状态，并且仅当 `IsPreviewMode` 为 false 时记录。

F8 已按特殊情况处理：`Finale.F8` 先展示公共剧情，再提供 F9、F10 和“担心身体”三个去向。因此：

- 进入 F8 本身不代表达成 F8。
- 选择“担心身体”并走完这条结局，才设置 `Ending_F8_Achieved = true`。
- 从 F8 继续进入 F9 或 F10，只记录实际到达的 F9 或 F10，不记录 F8。
- 从开发者菜单预览 F8/F9/F10 时，所有达成标记都不变。

这样可以解决 F8 既是分流节点又被计作结局的问题。

### 4.2 `CountFinale` 只统计达成标记

当前 `CountFinale` 已从 Knot 访问状态改为统计 `Ending_F1_Achieved` 至 `Ending_F11_Achieved`：

- 访问某个 Knot 不再自动等于达成结局。
- `FinaleCount` 表示正片已达成的不同结局数量。
- `TheEnd` 和“更多信息”中的结局回顾入口可以继续调用 `CountFinale`，但计算来源必须是达成状态。

### 4.3 `FinaleList` 只看达成标记

`FinaleList` 已将类似 `{Finale.F1}` 的显示条件替换为对应的 `Ending_F1_Achieved` 条件。这样：

- 通过正片达成过的结局会显示在回顾中。
- 仅通过开发者菜单看过的结局不会显示在正式回顾中。
- 多周目达成的结局会持续保留，直到玩家使用会重置整个 Ink 状态的 RESTART。

### 4.4 开发者菜单继续保留，但与正式回顾分离

已保留现有多次点击解锁开发者菜单的机制，以及 `All_Finale` 中直接进入各结局的预览入口。

开发者菜单的作用是**方便作者查看内容**，而不是伪造正式游玩记录。因此 `FinaleList` 与 `All_Finale` 的每条预览入口现在都会在跳转前设置 `IsPreviewMode = true`。正式结局回顾不依赖 Knot 访问记录。

F9/F10 的多周目条件也已从 Knot 访问状态改为正片达成状态：

- F9：`Ending_F2_Achieved` 为真时可见。
- F10：`Ending_F2_Achieved` 与 `Ending_F7_Achieved` 均为真时可见。

这样，开发者直接预览 F2 或 F7 不会意外解锁正片隐藏路线。若作者希望开发菜单也能强制解锁隐藏路线，应另设显式开发开关，而不是依赖副作用。

## 5. 宿舍线分支条件

作者于 2026-10-29 确认：按 RAW 原稿的“好感度 + 大体偏向”分流，取代临时方案（`Choose_X > 0` 资格判断 + 夜痕 → 岑烨 → 雷琥固定优先级）。已实现的规则：

1. `Rate_LeiHu >= 3` 时进入 F8。
2. `Rate_LeiHu < 3` 且 `Dormitory_LeiHu_Direct` 为真时，直接进入 F7。
3. 否则按唯一最高计数分流：`Choose_YeHen > Choose_CenYe && Choose_YeHen > Choose_LeiHu` → F5；`Choose_CenYe > Choose_YeHen && Choose_CenYe > Choose_LeiHu` → F6；`Choose_LeiHu > Choose_YeHen && Choose_LeiHu > Choose_CenYe` → F7。
4. 没有唯一最高（全零、两方或三方平局）时保留末尾默认 `-> Finale.F7`。

配套的选项级变化（对应 RAW 的 A/B/C 标注）：

- 开场“夜痕的事”：`Choose_YeHen++`，好感不变。
- 开场“岑烨的事”：`Choose_CenYe++`，不再增加好感。
- 开场“雷琥的事”：`Rate_LeiHu++`、`Choose_LeiHu++`，并设置 `Dormitory_LeiHu_Direct = true`。
- 追问后的“是啥样的活，工资高吗？”与“会不会累？”两个三级分支各 `Rate_LeiHu++`（RAW 352-359 均标注好感提升；后者 2026-10-29 补齐）。

全部条件都写成两个明确的数值比较，不恢复 `A > (B or C)` 这类把逻辑 `or` 当数值用的隐式写法；`G_Dormitory.RouteDecision` 作为测试锚点保留。保留现有计数变量与 `ShowData` 调试输出；本次只调整路线条件与上述选项增减，不删除计数功能。
